# 研究流程与文档规范

本文档规定后续每次工作必须遵守的流程。目标是保证论文改进基于可复现实验，
同时避免记录散乱、路径混乱和结论不可追溯。

## 1. 工作闭环

每次改进按以下顺序进行：

1. **确认目标**：说明本轮主要解决论文、实验、代码或文档中的哪个问题。
2. **读取上下文**：检查当前主稿、相关实验脚本、结果文件和已有记录。
3. **提出设计**：写清楚假设、对照组、指标、样本规模和预期可证伪点。
4. **实现改动**：代码、论文和文档改动必须小步完成，避免大块不可审查修改。
5. **运行验证**：至少运行对应 smoke；正式结果进入论文前必须运行 paper profile。
6. **记录结果**：更新实验报告、迭代日志、当前状态和复现说明。
7. **结构检查**：运行 `python run.py quick`；交付前运行
   `python run.py preflight`。实验运行和论文编译必须分离：实验命令写入
   `results/`、`figures/` 和 `docs/experiments/`，论文只由 `python run.py paper`、
   `python run.py comml-paper` 或对应 preflight 编译。
8. **说明不足**：明确当前仍不能支撑的结论和下一轮改进措施。

## 2. 文档分工

不同类型内容写入不同位置：

- `docs/PROJECT_STATUS.md`：当前版本状态、主结论、主要不足、下一步计划。
- `docs/reproducibility.md`：命令、输出路径、正式数据规模、smoke 隔离路径。
- `docs/experiments/`：实验设计和自动结果报告。
- `docs/reviews/`：问题审查、投稿准备度、同类论文差距。
- `docs/logs/`：阶段性迭代记录。
- `docs/literature/`：文献调研和参考文献依据。
- `docs/registry/`：数据、图表和论文产物登记表。

不要把同一类内容复制到多个位置。需要引用时使用相对路径。

## 3. 实验记录模板

每个新增实验或重要实验改动至少包含：

````md

## 研究问题

本实验试图验证或反驳什么结论。

## 设计

- 方法/算法：
- 对照组：
- 干扰机/信道/接收机：
- 指标：
- 样本规模：
- 随机种子：

## 运行

```sh
命令
```

## 输出

- 数据：
- 图：
- 自动报告：
- 论文引用位置：

## 结果

核心数值和置信区间。

## 解释与边界

哪些结论被支持，哪些不能宣称。

## 下一步

最小改进措施。
````

## 4. 迭代日志模板

迭代日志放入 `docs/logs/`，只记录研究决策：

```md
## YYYY-MM-DD：主题

### 背景问题

### 本轮改动

### 运行与验证

### 结果摘要

### 当前不足

### 下一步措施
```

## 5. 命名规范

- 阶段实验报告：`docs/experiments/<phase>_<topic>_results.md`
- 实验设计：`docs/experiments/<phase>_<topic>_design.md`
- 迭代日志：`docs/logs/<phase>_iteration_log.md`
- 审查报告：`docs/reviews/<topic>_review.md`
- 文献调研：`docs/literature/<topic>.md`

已有历史文件不强制重命名，但新增文件必须遵守该规则。

## 6. 复现原则

- 正式实验只写入 `results/<phase>/` 和 `figures/<phase>/`。
- smoke 输出必须写入 `tmp/`，不能覆盖正式数据。
- 论文引用的每个数字必须能追溯到 CSV/JSON 或自动结果报告。
- 当前 CommL 正式 PDF 是 `output/pdf/comml_ieee.pdf`。
- `paper/comml_ieee.pdf` 是 CommL 编译工作副本，应与交付 PDF 哈希一致。
- 新增正式数据、图表或论文产物时，必须同步更新 `docs/registry/`。

## 7. 汇报格式

每次工作结束必须向用户说明：

1. 本次主要工作。
2. 是否重新跑实验，运行目录和命令是什么。
3. 新结果保存在哪里。
4. 论文/PDF 是否重新生成。
5. 当前不足。
6. 下一步改进措施。
7. 是否更新了 registry 和 changelog。
